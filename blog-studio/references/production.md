# Visuals, export and delivery

Input: a mature article or a request to plan or produce visuals. Decide whether a reader needs a comparison, sequence, system relationship, distribution, geographic view or merely an atmosphere. Choose a table, flow diagram, chart, map or cover accordingly; don't impose an image quota. A cover sets context or mood and must not be treated as proof. An explanatory figure carries claims and must be checked against sources. For a series, reuse a restrained palette, type and visual vocabulary while allowing each figure's content to dictate its form.

For an explanation, specify placement, purpose, factual inputs and sources, entities and labels, relationships and arrow direction, reading order, layout, legend and meaning of colors, caption and alt text. Example: “client → cache; cache miss → database; database → cache” makes direction explicit. A pretty box-and-arrow picture without a defined arrow meaning can imply the wrong data flow. For data charts specify units, range, data and transformations; use deterministic plotting or diagrams, not an art model for exact facts. A generated image is not a real screenshot. Record prompts, inputs, versions and local assets if used, so a figure can be recreated.

When a suitable free local tool exists and the request warrants it, actually render the figure, inspect it at intended size for labels, overlaps, contrast, direction and factual accuracy, correct problems and link the final asset from a derived article. If unavailable, deliver a clearly marked placeholder or prompt; do not claim an image was made. Paid generation and external transmission require separate authorization and a budget when applicable.

Keep standard Markdown as the master. Produce formatted, translated and platform-specific copies separately; compare text against the master and respect locks. For HTML or another export, inspect the rendered output, not just the existence of a file. Check features the article actually uses: Chinese font and punctuation, code and wrapping, tables and overflow, equations, footnotes, links and relative image paths, and wide and narrow viewports. Report unsupported features and failed or uninspected rendering honestly. Avoid silently dropping content. Preview an export with host tools where available, and make a local correction and recheck if it breaks.

A local draft, remote draft, and public publication are distinct actions. Obtain explicit permission before remote upload or publishing, and before any paid service obtain budget approval. Don't automatically install dependencies, log in or transmit private materials. When capabilities or permissions are missing, return the master and honest actionable alternatives.

## Worked example: explanatory figure

Input: an article explains that a cache miss reads the database and then fills the cache before returning. The reader needs the direction of operations, not a decorative server room. Choose a flow diagram: request, cache, database and response are entities; arrows denote operations in order, not network topology. Distinguish hit and miss by labels as well as color. Give the return/fill paths separate arrows so the figure does not imply the database directly updates the client without a cache fill.

Reproducible specification: landscape SVG, white background, four labeled boxes “请求 / 缓存 / 数据库 / 返回”. Number arrows: ① 请求→缓存 “查询”; ② 缓存→返回 “命中”; ③ 缓存→数据库 “未命中，读取”; ④ 数据库→缓存 “填充”; ⑤ 缓存→返回 “返回”. Teal marks normal reading; amber marks the miss path; labels carry the distinction without color. Put ③–⑤ below the hit path, with no crossings; use readable Chinese labels. Caption: “简化读取顺序，不表示并发更新。” Alt text states both branches. A local vector editor or SVG generator can produce this exact structure; the SVG itself is the actual figure, not the prompt.

Before delivery, inspect the actual figure and linked article: do numbered arrows match the stated sequence, are Chinese labels legible at narrow width, is the key readable without color, and does the caption avoid claiming concurrent correctness? Check the SVG exists at the referenced path and that HTML/PDF preview loads it. If no pixel preview is available, say that visual acceptance is pending, even if XML parses. The example is illustrative, not an assertion about a particular service.

## Worked example: cover

Input: an article's central idea is that a streaming system waits for late events before closing a time window, trading latency against completeness. A cover suggests “waiting for a signal”: a stream of small dots crosses a wide dark field toward a translucent time window, with a few trailing dots outside it. The visual is atmosphere, not a literal measurement or proof of system behavior. Use landscape 16:9, place the window and dots on the right and reserve uncluttered left third for a later title; muted blue with one amber accent; no tiny text or fake interface. A usable prompt: “Editorial technology cover, 16:9; abstract stream of dots moving toward a translucent time window on the right, a few trailing dots, deep blue and restrained amber, calm technical mood, left third empty for title, no text, no logos or screenshots.”

When a reference image is supplied, say whether it informs content, visual style or palette; verify the actual file exists and can be used before invoking a generator. Do not treat an absent reference as available or imply its contents. Inspect the generated file for title space, aspect ratio, accidental text, visual clarity and misleading implied facts; confirm the saved asset and link. Without an authorized image tool, provide this clearly labeled prompt and layout instead of claiming a cover exists.
